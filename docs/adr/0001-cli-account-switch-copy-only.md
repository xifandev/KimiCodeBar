# CLI 账号切换：显式打破凭证隔离原则，采用「只复制、不同步」策略

KimiCodeBar 的多账号凭证历史上刻意与 Kimi Code CLI 的凭证文件（`~/.kimi-code/credentials/kimi-code.json`）完全隔离，因为服务端会轮换 refresh_token，两边共享同一对 token 必然互相踢掉。新增的「切换 CLI 到此账号」功能是这一原则**唯一的、显式的例外**：仅在用户主动触发切换的瞬间，把 Bar 账号的 token 一次性复制写入 CLI 凭证文件，此后两边各自独立、不再同步。

## Considered Options

- **双向同步（已拒绝）**：把 CLI 凭证文件作为活跃账号的唯一事实源，Bar 监听文件变化回读新 token。能消除冲突，但实现复杂度最高，且无法解决运行中的 CLI 会话持旧 token 覆写文件的竞态。
- **每次切换重新走设备授权（已拒绝）**：CLI 拿独立 refresh_token，彻底无冲突，但每次切换都要浏览器确认一次，不是一键切换。
- **只复制、不同步（采纳）**：实现最简单。代价是切换后任一方先刷新 token，另一方持有的 refresh_token 即失效——Bar 侧表现为该账号「登录失效」（引导重新授权），CLI 侧表现为需要重新 `kimi login`。用户已知情接受这一后果。

## Consequences

- 「CLI 使用中」标签靠实时比对 token 得出，CLI 轮换 token 后标签自然消失，这是预期行为而非 bug。
- 切换时若有运行中的 kimi 会话，其刷新 token 时会覆写本次切换，因此切换前会检测并提示用户先退出。
- 未来若要做双向同步，是对本决策的推翻，需要重新评审。
